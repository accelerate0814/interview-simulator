问 01
面试官
我们先从系统设计聊起。为一个日活百万的应用设计短链接服务的存储层，说说你的取舍。
答
你
先用关系型数据库存 长链 → 短码 的映射，短码用发号器生成，再加一层缓存扛读。写入量不大，读多写少。
问 02
面试官
那发号器怎么保证高可用？如果它挂了，整个写入链路就断了。有没有备选方案？
答
你
可以给发号器做主备切换，或者用号段模式——每个实例一次领一批 ID 段，本地发完再来领；这样即使中心节点短时间不可用，已经领到段的实例还能继续写。

逐题回顾
Q1 7/10
为一个日活百万的应用设计短链接服务的存储层，说说取舍。
你的回答
用关系型数据库存映射，短码用发号器生成，加缓存扛读。读多写少。
参考答案
关键点：短码生成策略（发号器 / hash / 预生成池）、存储选型与容量估算、缓存与热点、301 vs 302、防刷与过期。能主动给出 QPS 与存储量的量级估算是加分项。
点评
方向对，但没做容量估算，也没提发号器的高可用；追问后才补上。
总体评价
做得好的
—基础结构清晰，能快速给出可行方案
—愿意在追问下修正
可以更好的
—缺少量级估算的习惯
—高可用、容灾常被漏掉
建议补的
—容量估算：QPS / 存储 / 带宽的口算
—分布式发号器：Snowflake、号段模式
